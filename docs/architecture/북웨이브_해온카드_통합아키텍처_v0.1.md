# 북웨이브·Mock PG·해온카드 통합 아키텍처 v0.1

작성 목적: 2인 팀이 WSL2와 Docker Compose에서 동일한 실습 환경을 재현하고, 북웨이브 공격·PG 신뢰 경계·해온카드 동시 승인을 서로 섞지 않도록 서비스 책임을 고정한다.

현재 상태: `bookwave-app`과 `mock-pg`는 Java 21 + Spring Boot 최소 뼈대가 연결되었고, `haeon-card`는 Java 21 + Spring Boot·JDBC 기반 정상 승인·거절 경로까지 구현을 시작했다. `bookwave-chatbot`·`bookwave-cover-upload`는 실제 애플리케이션 교체 전 기준선이다.

## 1. 한 줄 요약

북웨이브 앱은 주문을 만들고, 챗봇과 표지·업로드 서비스는 DMZ에 분리 배치한다. 결제는 Mock PG를 통해서만 해온카드로 들어가며, 해온카드는 자기 승인 원본과 한도 장부만 책임진다.

## 2. 서비스 구성

| 서비스 | 기본 포트 | 네트워크 | 소유 데이터 | 역할 |
|---|---:|---|---|---|
| `bookwave-app` | 8080 | `front_net`, `dmz_net` | 북웨이브 주문·재고 | 앱 화면과 주문 API |
| `bookwave-chatbot` | 8081 | `dmz_net`, `bookwave_db_net` | 챗봇 대화·요청 기록 | 챗봇 요청과 표지 검색 호출 |
| `bookwave-cover-upload` | 8082 | `dmz_net` | 업로드·표지 실습 자료 | SCN-05A/05B 전용 경계 서비스 |
| `mock-pg` | 8083 | `dmz_net`, `card_net`, `audit_net` | PG 거래·콜백 원문 | 북웨이브와 해온카드 사이의 전달자. Spring Boot 뼈대 구현 |
| `haeon-card` | 8084 | `card_net`, `audit_net` | 카드·한도·승인·거래·감사 | OD-02-X 및 CARD-03 승인 코어 |
| `bookwave-mysql` | 3306 내부 | `bookwave_db_net` | 북웨이브 데이터 | 북웨이브 전용 DB |
| `haeon-card-mysql` | 3306 내부 | `card_net` | 해온카드 H0 스키마 | 해온카드 전용 DB |
| `evidence` | 없음 | `audit_net` | 실행 증거 파일 | 읽기 중심 증거 보관 |

포트 번호는 예약값이다. 실제 Spring Boot가 기동되면 같은 포트를 유지하고 `/actuator/health`를 제공한다.

## 3. 왜 컨테이너를 나누는가

`bookwave-chatbot`과 `bookwave-cover-upload`는 같은 Compose 프로젝트와 DMZ 네트워크에 있지만 서로 다른 컨테이너다. 그래서 “챗봇이 표지·업로드 서비스에 요청한다”는 경계를 로그와 네트워크 흐름으로 보여 줄 수 있다.

- SCN-05A: 챗봇 또는 표지 검색 요청이 서버 측 주소 요청으로 이어지는 경로
- SCN-05B: 상담 첨부파일의 검사·저장·실행 처리를 시험하는 경로
- 두 경로는 서로 다른 최초 진입 후보다.
- 두 경로가 해온카드나 PG를 먼저 침해해야 하는 구조는 아니다.

`bookwave-cover-upload`는 우선 Java/Spring 실습 서비스로 시작한다. 팀이 SCN-05B를 레거시 동작으로 재현하기로 확정하면 Apache/PHP 이미지를 이 컨테이너에만 교체한다. 다른 서비스에 PHP 런타임을 넣지 않는다.

## 4. 통신 규칙

```text
앱 → bookwave-app → bookwave-chatbot / cover-upload
bookwave-app → mock-pg → haeon-card
haeon-card → haeon-card-mysql
bookwave-chatbot → bookwave-mysql
각 서비스 로그 → 수집기/호스트 볼륨 → evidence (증거 기록만)
```

- `bookwave-app`은 해온카드 DB와 API를 직접 호출하지 않는다.
- `mock-pg`만 해온카드 승인 API를 호출한다.
- `haeon-card`는 북웨이브 주문 상태를 변경하지 않는다.
- 애플리케이션은 `evidence`를 업무 DB처럼 직접 쓰지 않고, 구조화 로그와 실행 manifest를 수집 경로로 보낸다.
- DB 간 직접 조인은 하지 않는다.

## 5. 공통 식별자

| 값 | 만드는 곳 | 모든 구간에서의 규칙 |
|---|---|---|
| `run_id` | 실습 제어기 | `BW05A-`, `BW05B-`, `ODX-`, `HC03-` 접두어로 분리 |
| `correlation_id` | 최초 결제 요청 | 북웨이브·PG·해온카드 왕복에서 동일 |
| `order_no` | 북웨이브 | 다른 주문과 재사용 금지 |
| `pg_tid` | Mock PG | PG 거래 하나에 하나만 발급 |
| `merchant_request_id` | 가맹점 요청 | 같은 가맹점·같은 키는 확정 결과 하나만 허용 |
| `auth_no` | 해온카드 | 카드 승인 원본의 번호 |

## 6. 실행 프로파일

| 프로파일 | 목적 | 허용 오류 |
|---|---|---|
| `normal` | 정상 승인·정상 거절 왕복 | 없음 |
| `before` | 취약한 동작을 관찰 | 승인된 랩에서만 Mock PG 또는 카드 코어 훅 활성화 |
| `after` | 개선 후 차단 확인 | 불일치 격리·최신 한도 재판정 |
| `test` | 회귀·초기화·증거 수집 | 합성 fixture만 사용 |

한 실행에서 OD-02-X와 CARD-03의 성공 조건을 동시에 켜지 않는다. PG 결정 불일치는 OD-02-X, 검증을 통과한 요청 두 건의 한도 초과는 CARD-03으로 판정한다.

## 7. 개발 순서

1. Compose 네트워크·볼륨·환경 변수 생성
2. 모든 컨테이너 health check 통과
3. 해온카드 H0 DB 초기화와 승인 API 뼈대
4. Mock PG 정상 승인·거절 전달 뼈대
5. 북웨이브 결제 접수 API와 주문 상태 뼈대
6. 같은 `correlation_id`로 세 시스템 로그 연결
7. OD-02-X Before/After 오류 주입
8. CARD-03 Before/After 동시 승인
9. 최종 선택한 북웨이브 SCN-05A 또는 SCN-05B

## 8. 오늘의 완료 기준

- `docker compose config`가 오류 없이 통과한다.
- Compose 프로젝트가 다섯 네트워크와 두 DB 볼륨을 만든다.
- 북웨이브 컨테이너가 해온카드 DB에 직접 연결할 수 없다.
- Mock PG만 `card_net`에 접근한다.
- 실제 결제·금융망·실제 카드정보가 환경 변수와 로그에 없다.
- 다음 작업자가 포트·네트워크·책임 경계를 문서만 보고 재현할 수 있다.

## 9. 선행 결정이 필요한 항목

- 북웨이브 표지 검색 서버 명칭을 `bookwave-chatbot`과 `bookwave-cover-upload`로 확정할지
- SCN-05B를 Java/Spring 취약 파일 처리로 구현할지, Apache/PHP 전용 레거시 컨테이너로 재현할지
- 앱 구현 범위가 화면만인지, `bookwave-app` 주문 API까지 포함하는지
- 북웨이브 최종 최초 진입을 SCN-05A와 SCN-05B 중 하나로 선택할지

이 항목들은 해온카드의 DDL·ERD를 바꾸는 결정이 아니라 북웨이브 실습 경계를 확정하는 결정이다.
