# 해온카드 결제 연동 진단 API 침해 시나리오 v0.2

결정일: 2026-09-21
상태: 서버 우선 MVP 구현·로컬 Docker 검증 완료 / 공격 시연 사이트 후속
시나리오 ID: HAEON-DIAG-01

## 1. 확정한 방향과 담당 범위

해온카드의 결제 연동 진단 API를 최초 공격 지점으로 삼는다. 입력 처리의 명령 주입 결함을 제한된 실습 방식으로 재현하고, 모의 웹쉘을 통한 합성정보 접근·반출과 탐지·차단을 비교한다.

- 사용자의 담당 범위는 해온카드다.
- 현재 Docker의 bookwave-app, bookwave-chatbot, bookwave-cover-upload는 임시 연동용 구성이다. 팀원이 개발한 실제 북웨이브와 별개이며, 이번 시나리오에서 수정하지 않는다.
- 북웨이브 자체 공격: 챗봇 → 북웨이브 서버 → 랜섬웨어 감염. 상세 진입 취약점은 북웨이브 담당 범위다.
- PG 연동 시나리오: 북웨이브 → Mock PG → 해온카드 사이의 신뢰 경계. 구체적 공격 설계는 별도다.
- 해온카드 자체 공격: 공격자가 해온카드의 웹/API에 직접 접근한다. 북웨이브 또는 PG 침해를 선행 조건으로 두지 않는다.
- 기존 CARD-03 동시 승인·한도 초과 실습은 별도 보조 시나리오로 유지한다.

도메인은 공개 서비스에 도달하는 주소다. 도메인 접속 자체와 최초 침입을 구분하며, 권한 없는 동작이 성립한 단계부터 침해로 판정한다.

## 2. 정상 업무 기능과 공격자 시작 조건

새로 추가할 기능은 가맹점 지원 화면의 '결제 연동 상태 진단'이다. 합성 가맹점 사용자가 사전에 등록된 실습용 연동 대상의 연결 상태를 확인한다. 실제 PG 호출이나 결제 승인을 수행하는 기능은 아니다.

- 화면 후보: 해온카드 → 가맹점 지원 → 결제 연동 상태 진단
- API 후보: POST /merchant/v1/diagnostics/connectivity
- 시작 권한: 일반 합성 가맹점 계정. 관리자·서버·DB 권한 없음
- 초기 조건: 가맹점 계정은 제공된 실습 계정이며 계정 탈취는 시나리오 범위에 포함하지 않음
- 정상 입력: 등록된 실습 대상 식별자와 제한된 진단 옵션
- 정상 결과: 대상의 연결 성공·실패와 소요 시간

위 경로와 화면은 설계안이며 현재 존재하는 API가 아니다. 회원 계정과 가맹점 계정의 역할을 분리한다.

## 3. 취약점과 모의 실행의 의미

최초 취약점은 진단 요청의 외부 입력을 명령 처리에 안전하지 않게 전달하는 결함이다. 모의 웹쉘은 이 결함 이후의 접근 수단이며 최초 취약점 자체가 아니다.

기본 구현 방향은 제한된 실습 실행기다. 임의 운영체제 명령을 실행하지 않고, 진단·모의 세션 생성·지정 합성자료 조회·지정 수신기로 전송이라는 고정된 종류의 동작만 처리한다. 모의 웹쉘은 이 동작을 호출하는 제한된 HTTP 인터페이스다.

단순히 성공 로그를 출력해서는 안 된다. 요청 내용과 실행 모드에 따라 허용되지 않은 실습 동작이 실제로 거부되거나, 모의 세션·합성자료 조회·수신 결과가 생성되어야 한다. 세션 없이 조회할 수 없고, 선행 단계가 실패하면 후속 단계도 실패해야 한다.

이 방식의 증거는 '명령 주입 흐름 및 모의 웹쉘의 제한된 재현'을 뒷받침한다. 실제 OS 명령 실행, 실제 웹쉘 설치, 운영 서버 장악을 입증한다고 표현하지 않는다. 실제 명령 실행 검증이 필수로 변경되면 실행 환경과 범위를 별도 설계한다.

## 4. 공격 단계와 필요한 증거

| 단계 | 동작 | 판정에 필요한 증거 |
|---|---|---|
| S0 정상 기준선 | 합성 가맹점 로그인 및 정상 진단 | 인증 주체, 요청·응답, 정상 진단 결과 |
| S1 최초 진입 | 해온카드 진단 API에 비정상 진단 요청 | 해당 요청이 허용되지 않은 실습 동작으로 이어졌는지 또는 거부됐는지 |
| S2 모의 웹쉘 | S1에서 생성한 모의 세션으로 제한된 인터페이스 접근 | 세션 생성·검증 기록, 세션 없는 요청의 거부 |
| S3 정보 접근 | 지정된 합성 결제 지원 자료 조회 | 실제 반환된 합성 레코드 수·자료 식별자·조회 감사 기록 |
| S4 반출 시도 | 지정된 실습용 수신 서버로 해당 자료 전송 | 송신 결과와 수신 서버의 같은 실행 ID·건수·해시 대사 |
| S5 대응 | 모의 세션 폐기, 자료 접근·반출 통제 | 재접근·재전송 거부 및 새 수신 자료가 없음을 확인 |
| S6 고객 보호·정상성 | 영향받은 합성 회원 식별 및 보호 상태 표시 | 실제 랩 상태 변경, 정상 진단·기존 결제 기능 회귀 결과 |

S6의 고객 보호는 합성 회원 대상 보호 안내·추가 확인 필요 상태를 랩 데이터에 기록하는 것으로 시작한다. 실제 알림 발송·카드 정지·결제 취소는 수행하지 않는다. 카드 정지까지 구현할 경우 기존 승인 로직과의 연계를 추가 검증해야 한다.

## 5. Before / After / 대응 실행 구분

| 실행 | 목적 | 기대 결과 |
|---|---|---|
| Before | 취약 처리와 정보 노출을 관찰 | S1~S4 실습 동작 성공, 수신 자료 확인, 탐지 이벤트 발생 |
| After | 예방 통제 검증 | 같은 의미의 비정상 요청을 진입 단계에서 거부, 모의 세션·조회·수신 자료 없음 |
| 대응 실행 | 이미 생성된 모의 세션에 대한 대응 검증 | Before에서 만든 세션 폐기 후 동일 세션의 조회·전송 실패 |

After에서 첫 단계가 막히면 나머지 공격 단계를 성공으로 표시하지 않는다. '선행 단계 차단으로 미실행'으로 표시한다. 초기 차단만으로 후속 통제 전체가 검증됐다고 주장하지 않는다.

정상 진단은 Before와 After 모두 성공해야 한다. 개선 기준은 외부 입력을 명령으로 해석하지 않는 처리, 등록 대상 허용 목록, 가맹점 권한 검사, 합성자료 최소 접근 권한, 반출 대상 제한이다.

## 6. 서비스와 데이터 경계

권장 배치는 기존 승인 코어와 별도의 해온카드 실습 지원 서비스다. 같은 해온카드 도메인에서 리버스 프록시가 /merchant 경로를 지원 서비스로 전달하도록 설계한다. 외부 진입은 프록시의 웹/API 경로로 수행한다.

```text
공격 시연 사이트 → 시나리오 실행 백엔드
                      ↓ 해온카드 도메인의 HTTP API
               해온카드 웹 진입점
                      ↓
               해온카드 진단 실습 서비스
                 ├─ 제한된 모의 웹쉘
                 ├─ 합성 결제 지원 자료
                 └─ 실습용 반출 수신 서버

독립된 정상 결제: 북웨이브 → Mock PG → 해온카드 승인 코어
```

- 승인 API 8084와 DB는 내부 전용 경계를 유지한다.
- 진단 서비스가 승인 DB 전체에 접근할 수 있다고 가정하지 않는다. 정보 접근 대상은 별도로 준비한 합성 결제 지원 자료다.
- 자료는 합성 회원 ID·카드 토큰·마스킹 번호·합성 거래 등으로 구성한다. 실제 카드정보나 기존 비밀 설정 파일을 사용하지 않는다.
- 반출 수신 서버는 지정된 랩 내부 대상이며 외부 임의 주소를 입력받지 않는다.
- 공개 진입점·서비스·수신기 간 연결과 권한은 후속 Compose 설계에서 검증한다.
- 도메인·DNS·TLS·EC2 주소는 아직 미정이다. 진단 서비스도 아직 배포되어 있지 않다.

## 7. 공격 시연 사이트

해온카드 회원 사이트와 별도로 만든다. 왼쪽은 실행 메뉴, 오른쪽은 요청·응답과 동작·로그를 표시한다.

왼쪽 메뉴: 환경 확인 / 정상 진단 / 진단 API 공격 / 모의 웹쉘 / 합성정보 조회 / 반출 시도 / 탐지·대응 / Before·After 비교 / 증거 다운로드.

오른쪽 표시: 현재 단계, 요청 대상·응답 코드, 모의 세션 상태, 조회·수신 건수, 시각별 로그, 차단 이유, 실행 ID와 상관관계 ID.

실행 백엔드는 사전 정의한 시나리오만 수행한다. 브라우저에 실습 제어 비밀을 넣거나 Docker 소켓·임의 셸 실행 권한을 제공하지 않는다. 사이트는 사전 작성된 성공 애니메이션이 아니라 대상 서비스와 수신기의 실제 결과를 보여 준다.

## 8. 실행 증거와 완료 기준

실행 ID 접두어는 HAEON-DIAG-를 사용한다. 대상·모드·fixture 버전·코드 버전·요청·응답·서비스 이벤트·수신 기록·통제 결과를 실행별로 남긴다. 토큰과 세션 원문은 증거에서 마스킹한다.

완료 기준:

1. 북웨이브 또는 Mock PG를 거치지 않고 해온카드 진단 시나리오를 독립 실행할 수 있다.
2. 일반 합성 가맹점의 정상 진단이 동작하고, 인증·권한 없는 호출은 거부된다.
3. Before의 모의 세션·자료 조회·수신 결과가 요청과 인과관계로 연결된다.
4. After는 같은 의미의 공격 요청을 차단하고 정상 진단을 유지한다.
5. 탐지 결과는 관측 이벤트에서 도출하며 ALERT·BLOCKED를 무조건 고정 반환하지 않는다.
6. 폐기된 세션으로 재접근·재전송할 수 없고 수신 증거가 이를 뒷받침한다.
7. 해온카드 회원 조회와 정상 결제 계약의 회귀 검증을 통과한다.
8. 공격 사이트에서 단계별 실제 결과와 실행별 증거를 확인할 수 있다.

## 9. 기존 구현과의 관계 및 구현 순서

기존 PAYMENT_SERVER_INCIDENT_V1은 bookwave-app에서 고정 이벤트 7개를 기록하는 시뮬레이션이다. 해온카드·Mock PG 호출, 실제 합성정보 조회·반출은 없다. 과거 실행 증거는 보존하되 HAEON-DIAG-01의 성공 증거로 재사용하지 않는다.

기존 v0.1 시나리오·촬영 자료·런북은 기존 구현 설명이다. 신규 구현 완료 전까지 현재 실행 방법으로 사용할 수 있으나, 새 해온카드 시나리오가 구현됐다고 발표하는 근거로 쓰지 않는다.

구현 순서:

1. 해온카드 진단 서비스·합성 가맹점 인증·정상 진단 API 및 fixture.
2. 제한된 취약 처리 경로와 모의 웹쉘 세션의 인과관계 구현.
3. 합성정보 접근·지정 수신기로 전송·수신 증거 구현.
4. 탐지·예방·세션 폐기·합성 고객 보호 상태 및 회귀 검증.
5. 별도 공격 시연 사이트와 증거 다운로드.
6. 신규 런북·촬영 자료 작성, Git 반영, 접근을 제한한 EC2 시연 배포.

현재 구현된 MVP는 해온카드 진단 서비스·가맹점 화면·제한된 모의 웹쉘·합성자료 20건 조회·내부 수신·자동 탐지·수동 대응·회원 보호 안내까지다. 별도 공격 시연 사이트, Git 원격 업로드, EC2 배포는 후속 범위다.

로컬 검증 결과 `HAEON-DIAG-20260921075152-2925`에서 Before 공격 `ALERT`, 합성자료 20건 수신 `RECEIVED`, 대응 후 `CONTAINED/BLOCKED`를 확인했다. 실행 증거는 `evidence/runs/HAEON-DIAG-20260921075152-2925/`에 있다. After는 동일한 의미의 `status;LAB_SHELL` 입력을 HTTP 403 `DIAGNOSTIC_INPUT_BLOCKED`로 차단한다.

## 10. 사례 인용 원칙과 참고

실제 카드사 사건에서는 결제 서버 침해·웹쉘·정보유출이라는 문제의식을 참고한다. '결제 연동 진단 API의 명령 주입'은 프로젝트가 선택한 실습 가정이며 실제 사건의 확정된 원인으로 제시하지 않는다.

- OWASP 명령 주입 방어: https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html
- MITRE 공개 서비스 취약점 악용: https://attack.mitre.org/techniques/T1190/
- MITRE Web Shell: https://attack.mitre.org/techniques/T1505/003/

제한된 재현이라는 한계를 표시하며 실제 ATT&CK 기법 실행을 모두 입증했다고 주장하지 않는다.
